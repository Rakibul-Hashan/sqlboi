## তিনটা মূল উপাদান

| উপাদান | কী | আমাদের স্কুলে | ছবিতে |
| --- | --- | --- | --- |
| **Entity** | যে "জিনিস" নিয়ে তথ্য রাখি | Student, Subject, Teacher | আয়তক্ষেত্র |
| **Attribute** | Entity-র বৈশিষ্ট্য | name, phone, salary | ডিম্বাকৃতি |
| **Relationship** | Entity-দের মধ্যে সম্পর্ক | Student *Takes* Subject | রম্বস |

একটা সহজ কৌশল: সিস্টেমের বর্ণনায় **বিশেষ্য** (noun) প্রায়ই Entity, **ক্রিয়া** (verb) প্রায়ই Relationship। "শিক্ষক বিষয় **পড়ান**, ছাত্র বিষয় **নেয়** আর নম্বর **পায়**।"

## Attribute-এর ধরন

| ধরন | মানে | উদাহরণ | ছবিতে |
| --- | --- | --- | --- |
| **Simple** | আর ভাঙা যায় না | `salary` | সাধারণ ডিম্বাকৃতি |
| **Composite** | ছোট অংশে ভাঙা যায় | ঠিকানা = বাড়ি + রাস্তা + শহর | ডিম্বাকৃতি থেকে আরও ডিম্বাকৃতি |
| **Multi-valued** | একাধিক মান থাকতে পারে | একজনের কয়েকটা `phone` | দুই দাগের ডিম্বাকৃতি |
| **Derived** | অন্য Attribute থেকে হিসাব করা যায় | `age` (জন্মতারিখ থেকে) | ড্যাশ দেওয়া ডিম্বাকৃতি |
| **Key** | Entity-কে অনন্যভাবে চেনায় | `id` | নামের নিচে দাগ |

লেভেল ৬-এ বয়স কেন টেবিলে রাখিনি, মনে আছে? সেটা ছিল Derived Attribute।

## Cardinality: কয়টার সাথে কয়টা

| ধরন | মানে | উদাহরণ |
| --- | --- | --- |
| **১:১** (One-to-One) | একটার সাথে সর্বোচ্চ একটা | একজন ছাত্র ↔ একটা পরিচয়পত্র |
| **১:N** (One-to-Many) | একটার সাথে অনেকগুলো, কিন্তু উল্টো দিকে একটা | একজন শিক্ষক → অনেক বিষয়; প্রতিটা বিষয়ের একজন শিক্ষক |
| **M:N** (Many-to-Many) | দুই দিকেই অনেক | ছাত্র অনেক বিষয় নেয়, প্রতিটা বিষয় অনেক ছাত্র নেয় |

ঠিক করার উপায়: **দুই দিক থেকে আলাদা করে একটা প্রশ্ন করো।**

- "একজন শিক্ষক কয়টা বিষয় পড়াতে পারেন?" → অনেক (N)
- "একটা বিষয় কয়জন শিক্ষক পড়ান?" → একজন (1)
- তাই Teacher : Subject = **১:N**

### Participation: সবাইকে কি থাকতেই হবে?

- **Total (সম্পূর্ণ)**: প্রতিটা Entity-কে সম্পর্কে থাকতেই হবে। প্রতিটা ছাত্রকে অন্তত একটা বিষয় নিতেই হবে। ছবিতে **দুই সমান্তরাল রেখা**।
- **Partial (আংশিক)**: থাকতেও পারে, না-ও পারে। প্রত্যেক শিক্ষকের বিষয় থাকবেই, এমন না (শারমিন ম্যাডামের মনে আছে?)। ছবিতে **এক রেখা**।

### Relationship-এরও Attribute থাকে

`score` কার বৈশিষ্ট্য? ছাত্রের না (রাফির একটা নম্বর না, তিনটা), বিষয়ের না (গণিতের একটা নম্বর না)। এটা "রাফি **গণিত নিয়েছে**" এই সম্পর্কের বৈশিষ্ট্য। তাই ছবিতে `score` ঝুলছে *Takes* রম্বস থেকে। আর এজন্যই `marks` টেবিলে `score` থাকে।

## Weak Entity

কিছু Entity নিজে নিজে চেনা যায় না, অন্য একটা Entity-র ওপর নির্ভর করে। অভিভাবক (Guardian): "আব্বু" নামে হাজারজন আছেন; কিন্তু "রাফির আব্বু" একজনই। Guardian হলো **Weak Entity**, Student তার **Owner**। ছবিতে দুই দাগের আয়তক্ষেত্র। এর Key হয় Owner-এর Key + নিজের আংশিক Key (**Partial Key**, যেমন `relation`: বাবা/মা)। Owner মুছে গেলে Weak Entity-রও অর্থ থাকে না।

## ER থেকে টেবিল: Mapping-এর নিয়ম

এটাই আসল দক্ষতা। প্রতিটা নিয়ম একটা করে SQL দিয়ে দেখি (জোন ২-এর `school` খাতায় চালাতে পারো)।

### নিয়ম ১: প্রতিটা সাধারণ Entity → একটা টেবিল

Key Attribute → `PRIMARY KEY`, Simple Attribute → Column, Composite → আলাদা আলাদা Column (`house`, `road`, `city`), Derived → কোনো Column না।

### নিয়ম ২: ১:N → "N" দিকের টেবিলে Foreign Key

একজন শিক্ষকের অনেক বিষয়, তাই `subjects`-এ `teacher_id`। উল্টো করে `teachers`-এ `subject_id` রাখলে একজন শিক্ষকের একটাই বিষয় রাখা যেত।

<Remember>
**১:N সম্পর্কে Foreign Key সবসময় "অনেক" (N) দিকের টেবিলে যায়।** "এক" দিকের টেবিলে রাখলে একটা ঘরে অনেকগুলো মান লাগত, যা Atomic নিয়ম ভাঙে।
</Remember>

### নিয়ম ৩: M:N → নতুন একটা Junction টেবিল

ছাত্র আর বিষয়ের মাঝে `marks`। দুই পাশের Primary Key এখানে Foreign Key হয়ে আসে, দুটো মিলে Composite Primary Key, আর Relationship-এর Attribute (`score`) এখানেই বসে। M:N সম্পর্ককে সরাসরি দুই টেবিলে Foreign Key দিয়ে রাখা **অসম্ভব**; Junction টেবিল লাগবেই। (এর আরেক নাম Bridge বা Associative টেবিল।)

### নিয়ম ৪: ১:১ → যেকোনো এক দিকে Foreign Key + UNIQUE

```sql
CREATE TABLE id_cards (
  student_id  INT PRIMARY KEY,                 -- Primary Key হওয়ায় নিজে থেকেই UNIQUE
  card_no     VARCHAR(20) NOT NULL UNIQUE,
  issued_on   DATE NOT NULL,
  FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE
);
```

`student_id` এখানে Primary Key **এবং** Foreign Key দুটোই, তাই একজন ছাত্রের দুটো কার্ড হতে পারে না। Foreign Key রাখো সেই দিকে যেখানে Participation সম্পূর্ণ (প্রতিটা কার্ডের একজন ছাত্র থাকতেই হবে, কিন্তু প্রতিটা ছাত্রের কার্ড না-ও থাকতে পারে), তাহলে `NULL` লাগবে না।

### নিয়ম ৫: Multi-valued Attribute → আলাদা টেবিল

```sql
CREATE TABLE student_phones (
  student_id INT NOT NULL,
  phone      VARCHAR(15) NOT NULL,
  label      ENUM('নিজের', 'বাবা', 'মা', 'অন্যান্য') NOT NULL DEFAULT 'নিজের',
  PRIMARY KEY (student_id, phone),
  FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE
);
```

`phone1`, `phone2`, `phone3` Column বানানো ভুল: তিনটার বেশি হলে? খোঁজার সময় তিনটা Column-এ খুঁজতে হবে? প্রতিটা নম্বর একটা Row।

### নিয়ম ৬: Weak Entity → Owner-এর Key + Partial Key = Primary Key

```sql
CREATE TABLE guardians (
  student_id INT NOT NULL,
  relation   ENUM('বাবা', 'মা', 'অভিভাবক') NOT NULL,   -- Partial Key
  name       VARCHAR(100) NOT NULL,
  phone      VARCHAR(15),
  PRIMARY KEY (student_id, relation),
  FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE
);
```

`ON DELETE CASCADE` ঠিক Weak Entity-র সংজ্ঞাই প্রয়োগ করছে: Owner গেলে সেও যাবে।

### সারাংশ

| ER-এ | MySQL-এ |
| --- | --- |
| Strong Entity | টেবিল + Primary Key |
| Weak Entity | টেবিল, PK = Owner-এর PK + Partial Key, `CASCADE` |
| Composite Attribute | কয়েকটা Column |
| Multi-valued Attribute | আলাদা টেবিল |
| Derived Attribute | Column না; Query বা View-তে হিসাব |
| ১:১ | এক দিকে FK + `UNIQUE` |
| ১:N | N দিকে FK |
| M:N | Junction টেবিল, Composite PK |
| Relationship-এর Attribute | ১:N-এ N দিকের টেবিলে, M:N-এ Junction-এ |

<Quest id="3" title="ভুল ধরো">
একজন জুনিয়র এই ডিজাইন বানাল: `courses(id, name, teacher_name, teacher_phone, student_ids)`, যেখানে `student_ids`-এ লেখা `"1,4,7"`। অন্তত তিনটা ভুল বের করো।

<Solution>
১. `student_ids`-এ একাধিক মান এক ঘরে: Atomic নিয়ম ভঙ্গ, আর M:N সম্পর্ককে লুকিয়ে রাখা। Junction টেবিল লাগবে।

**১. ER বিশ্লেষণ**

- Entity: Department, Doctor, Patient, Appointment, Medicine
- Department **১:N** Doctor (প্রত্যেক ডাক্তার একটা বিভাগে: Total participation)
- Patient **M:N** Doctor, সম্পর্কটার নিজস্ব অনেক Attribute আছে (সময়, ফি, প্রেসক্রিপশন), তাই একে নিজেই একটা Entity বানানো ভালো: **Appointment** (Patient ১:N Appointment, Doctor ১:N Appointment)
- Appointment **M:N** Medicine (একটা প্রেসক্রিপশনে অনেক ওষুধ, একটা ওষুধ অনেক প্রেসক্রিপশনে), Attribute `dose`
- Patient-এর `phone`: Multi-valued, আর `age`: Derived (রাখব না)

**২. টেবিল**

```sql
CREATE TABLE departments (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(80) NOT NULL UNIQUE
);

CREATE TABLE doctors (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  name          VARCHAR(100) NOT NULL,
  bmdc_no       VARCHAR(20) NOT NULL UNIQUE,        -- Natural Key, Alternate Key হিসেবে
  department_id INT NOT NULL,                       -- NOT NULL = Total participation
  FOREIGN KEY (department_id) REFERENCES departments(id)
);

CREATE TABLE patients (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  birth_date DATE
);

CREATE TABLE patient_phones (
  patient_id INT NOT NULL,
  phone      VARCHAR(15) NOT NULL,
  PRIMARY KEY (patient_id, phone),
  FOREIGN KEY (patient_id) REFERENCES patients(id) ON DELETE CASCADE
);

CREATE TABLE appointments (
  id           INT AUTO_INCREMENT PRIMARY KEY,
  patient_id   INT NOT NULL,
  doctor_id    INT NOT NULL,
  scheduled_at DATETIME NOT NULL,
  fee          DECIMAL(8,2) NOT NULL CHECK (fee >= 0),
  notes        TEXT,                                -- প্রেসক্রিপশনের সাধারণ লেখা
  UNIQUE (doctor_id, scheduled_at),                 -- একই সময়ে একজন ডাক্তারের দুই রোগী না
  FOREIGN KEY (patient_id) REFERENCES patients(id),
  FOREIGN KEY (doctor_id)  REFERENCES doctors(id)
);

CREATE TABLE medicines (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE prescription_items (
  appointment_id INT NOT NULL,
  medicine_id    INT NOT NULL,
  dose           VARCHAR(50) NOT NULL,              -- যেমন "১+০+১, খাবারের পরে"
  PRIMARY KEY (appointment_id, medicine_id),
  FOREIGN KEY (appointment_id) REFERENCES appointments(id) ON DELETE CASCADE,
  FOREIGN KEY (medicine_id)    REFERENCES medicines(id)
);
```

লক্ষ্য করো `UNIQUE (doctor_id, scheduled_at)`: একটা ব্যবসায়িক নিয়ম, যেটা ER Diagram-এ সহজে দেখানো যায় না, কিন্তু টেবিলে Constraint দিয়ে বসানো যায়। এই ডিজাইনটা পরের লেভেলে Normalization-এর চোখ দিয়ে আবার যাচাই করব।
</Solution>
