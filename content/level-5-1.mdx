<Story title="ফাঁকা পাতা">
রাফি `SELECT`, `JOIN`, `GROUP BY`, `HAVING`, Subquery সব জানে। প্রতিটার সংজ্ঞা বলতে পারে, উদাহরণ দেখলে বোঝে। কিন্তু অ্যাসাইনমেন্টের প্রশ্নটা পড়ার পর আধা ঘণ্টা ধরে ফাঁকা পাতার দিকে তাকিয়ে আছে: "Find the student ID and name of each student who has registered for every course taught by Dr. Rahman." কোথা থেকে শুরু করবে? `SELECT` লিখে থেমে আছে।

সমস্যাটা রাফির জ্ঞানে না, **পদ্ধতিতে**। সে প্রশ্নটা পুরোটা একবারে Query-তে রূপান্তর করতে চাইছে। কেউই সেটা পারে না, অভিজ্ঞরাও না। অভিজ্ঞরা শুধু জানে প্রশ্নটা কীভাবে টুকরো করতে হয়।
</Story>

## মূল কথা: SQL যে ক্রমে লিখি, সেই ক্রমে ভাবি না

রাফি `SELECT` লিখে আটকে গেল কেন? কারণ `SELECT` লেখার সময় তাকে জানতে হবে কোন Column আসবে, আর সেটা নির্ভর করে কোন টেবিল জোড়া হবে, কী ছাঁকা হবে, কীভাবে দল বাঁধা হবে, যেগুলো সে এখনো ভাবেইনি।

লেভেল ৮-এ দেখেছি MySQL নিজে Query কোন ক্রমে চালায়। ভাবতেও হবে সেই ক্রমে:

| লেখার ক্রম | চলার (আর ভাবার) ক্রম | যে প্রশ্নের উত্তর দেয় |
| --- | --- | --- |
| `SELECT` | ১. `FROM` / `JOIN` | তথ্য কোন কোন টেবিলে? কীভাবে জোড়া? |
| `FROM` / `JOIN` | ২. `WHERE` | কোন Row-গুলো বাদ? |
| `WHERE` | ৩. `GROUP BY` | Row-গুলোকে কী ধরে দল বাঁধব? |
| `GROUP BY` | ৪. `HAVING` | কোন দলগুলো বাদ? |
| `HAVING` | ৫. `SELECT` | শেষে কী দেখাব? |
| `ORDER BY` | ৬. `ORDER BY` / `LIMIT` | কোন ক্রমে, কয়টা? |

<Remember>
**Query লেখা শুরু করো `FROM` থেকে, `SELECT` থেকে না।** প্রথমে `SELECT *` লিখে রাখো, `FROM` আর `JOIN` ঠিক করো, চালাও, দেখো কী এল। `SELECT`-এর আসল Column-গুলো বসাও একদম শেষে।
</Remember>

আর এর আগে, প্রতিটা নতুন Database-এ **একবার**: টেবিলগুলো চেনা।

### শুরুর আগে একবার: Database চেনা

প্রশ্নের দিকে তাকানোর আগে তিনটা জিনিস জেনে নাও:

1. **কোন টেবিলে কী আছে।** প্রতিটা Column-এর মানে। যেমন `orders`-এ টাকার অঙ্ক নেই; অঙ্ক = `product.price × orders.quantity`।
2. **কোন Column কোনটার সাথে মেলে** (Foreign Key)। কাগজে তীর এঁকে নাও: `customer.cust_id ← orders.cust_id`, `orders.prod_id → product.prod_id`। একটা টেবিল থেকে আরেকটায় যাওয়ার এটাই রাস্তা।
3. **ডেটার অদ্ভুত দিক।** কোথায় `NULL` আছে? কার কোনো Row নেই? সমান মান আছে? Primary Key-তে কয়টা Column (মানে কী ডুপ্লিকেট হতে পারে)?

প্রবলেমের পাতাগুলোয় প্রথম অংশ সবসময় "Database চেনা"। ওটা বাদ দিয়ে সরাসরি উত্তরে যেয়ো না।

### ধাপ ১: নিজের ভাষায় বলো

প্রশ্নটা নিজের ভাষায় একবার বলো, আর সবচেয়ে জরুরি প্রশ্নের উত্তর দাও: **"উত্তরের প্রতিটা Row-তে কী থাকবে?"** একজন ক্রেতা? একটা অর্ডার? একটা ক্যাটাগরি? নাকি পুরো উত্তর একটাই সংখ্যা?

এটাকে বলে উত্তরের **গ্রেইন** (Grain)। গ্রেইন ঠিক হলেই অর্ধেক কাজ শেষ:

| প্রতি Row-তে... | তাহলে... |
| --- | --- |
| একজন ক্রেতা, একবার | `DISTINCT`, বা `EXISTS`, বা `GROUP BY cust_id` লাগবে |
| একটা ক্যাটাগরি | `GROUP BY category` |
| একটাই সংখ্যা | কোনো `GROUP BY` না (বা ভেতরে দল, বাইরে Aggregate) |
| একটা অর্ডার | কোনো দল না, শুধু JOIN আর ছাঁকা |

### ধাপ ২: শব্দ দাগাও

প্রশ্নের প্রতিটা টুকরোর নিচে দাগ দাও, আর পাশে লেখো সেটা SQL-এর কোন অংশ। নিচের অভিধানটা এই কাজের জন্যই। অ্যাসাইনমেন্টের প্রশ্ন ইংরেজিতে আসে, তাই দুই ভাষাতেই দিলাম:

| প্রশ্নে লেখা | মানে | SQL-এ |
| --- | --- | --- |
| "find the name and city", "return ...", "show details" | আউটপুট | `SELECT` (details = `*`) |
| "each", "per", "for every category" (গ্রেইন বোঝাতে), "প্রতি" | দল | `GROUP BY` |
| "total", "sum", "মোট" | যোগ | `SUM(...)` |
| "number of", "how many", "কয়টা" | গোনা | `COUNT(...)` |
| "average", "গড়" | গড় | `AVG(...)` |
| "whose total exceeds ...", "দলের মোট ... এর বেশি" | দলের শর্ত | `HAVING` |
| "in 2025", "after 1 Jan", "from branch 101" | Row-এর শর্ত | `WHERE` |
| "101 or 104", "10 or 40" | এক Column, কয়েকটা মান | `IN (...)` |
| "at least one", "any", "some", "অন্তত একটা" | অস্তিত্ব | `EXISTS`, বা `JOIN` + `DISTINCT` |
| "never", "not any", "has not", "কখনো না" | অনস্তিত্ব | `NOT EXISTS`, `LEFT JOIN ... IS NULL`, Algebra-তে − |
| "every", "all" (একটা সেটের), "প্রতিটা", "সবগুলো" | Relational Division | দুইবার `NOT EXISTS`, বা `COUNT(DISTINCT)` মেলানো |
| "most expensive", "highest", "maximum", "সবচেয়ে" | সর্বোচ্চের সমান | `= (SELECT MAX(...))` |
| "greater than the average of **his own** branch" | নিজের দলের সাথে তুলনা | Correlated Subquery |
| "together with the name of his supervisor" | একই টেবিল দুই ভূমিকায় | Self Join |
| "must still be counted", "including those with none" | শূন্যদেরও রাখো | `LEFT JOIN` + `COUNT(ডান.col)` |
| "sorted by salary in descending order" | সাজানো | `ORDER BY salary DESC` |
| "create a view" | নাম দিয়ে রাখো | `CREATE VIEW ... AS` |

দাগ দেওয়ার পর প্রতিটা শর্তের পাশে লেখো, সেটা **কোন টেবিলের কোন Column**-এর ওপর। "CSE department" কথাটা `student.dept` নাকি `course.offered_by`? এই এক প্রশ্নেই অনেক ভুল ধরা পড়ে (প্রবলেম ১ দেখো)।

### ধাপ ৩: হাতে উত্তর বানাও

Query লেখার **আগে**, ডেটা দেখে নিজে উত্তরটা বের করো। নমুনা ডেটা ছোট, তাই ২-৩ মিনিট লাগে।

কেন? কারণ Query চললেই সেটা সঠিক না। SQL-এর সবচেয়ে বিপজ্জনক ভুলগুলো **কোনো error দেয় না**, শুধু চুপচাপ একটা বাড়তি নাম ঢুকিয়ে দেয় বা একজনকে বাদ দেয়। আগে থেকে উত্তর জানা থাকলে সেটা এক নজরে ধরা পড়ে; না জানলে "দেখতে তো ঠিকই লাগছে" ভেবে জমা দিয়ে দেবে।

হাতে উত্তর বানাতে গিয়েই প্রায়ই প্রশ্নের অস্পষ্টতা চোখে পড়ে: "after 1 January" মানে ১ জানুয়ারি সহ, নাকি বাদ? একই কোর্স দুবার নিলে দুটো গুনব, নাকি একটা?

### ধাপ ৪: ছোট ধাপে বানাও, প্রতি ধাপে চালাও

এখানেই আসল "ভাঙা"। বড় প্রশ্নের ভেতরে প্রায় সবসময় এক বা একাধিক **ছোট প্রশ্ন** লুকিয়ে থাকে:

- "সবচেয়ে দামি পণ্যের ক্রেতা" → ছোট প্রশ্ন: সর্বোচ্চ দাম কত? কোন পণ্যের?
- "নিজের ব্রাঞ্চের গড়ের চেয়ে বেশি" → ছোট প্রশ্ন: প্রতিটা ব্রাঞ্চের গড় কত?
- "গড়ে কয়টা কোর্স, শূন্যসহ" → ছোট প্রশ্ন: প্রত্যেকে কয়টা নিয়েছে?

প্রতিটা ছোট প্রশ্ন **আলাদা Query হিসেবে লিখে চালাও**, উত্তর দেখো। তারপর সেটাকে বড়টার ভেতরে বসাও (Subquery, Derived Table বা CTE হিসেবে)। আর বড় Query-টাও একবারে না লিখে স্তরে স্তরে:

1. `FROM` আর `JOIN`, সাথে `SELECT *`। চালাও। কয়টা Row এল? প্রত্যাশামতো?
2. `WHERE` যোগ করো। চালাও।
3. `GROUP BY` আর Aggregate। চালাও।
4. `HAVING`। চালাও।
5. শেষে `SELECT`-এ শুধু প্রশ্নের চাওয়া Column, আর `ORDER BY`।

প্রতিটা ধাপে Row-এর সংখ্যা দেখো। হঠাৎ অনেক বেড়ে গেলে কোনো JOIN ডুপ্লিকেট বানাচ্ছে; হঠাৎ কমে গেলে কোনো JOIN বা শর্ত কাউকে ফেলে দিচ্ছে।

### ধাপ ৫: মেলাও

শেষ Query-র উত্তর ধাপ ৩-এর হাতের উত্তরের সাথে মেলাও, নাম ধরে ধরে। না মিললে, হয় Query ভুল, নয়তো হাতের হিসাব; দুটোই আবার দেখো। মিলে গেলেই শেষ না, পরের ধাপ বাকি।

### ধাপ ৬: নিজের Query ভাঙার চেষ্টা করো

নমুনা ডেটায় সঠিক উত্তর আসা মানে Query সঠিক, এমন না; হয়তো ডেটায় ফাঁদের কেসটাই নেই। নিজেকে জিজ্ঞেস করো:

| ফাঁদ | নিজেকে প্রশ্ন |
| --- | --- |
| **ডুপ্লিকেট** | JOIN-এর পর একই জন একাধিকবার আসতে পারে? (`DISTINCT` / `EXISTS`) |
| **খালি দল** | যার কোনো Row নেই (কোনো অর্ডার দেয়নি), সে কি হারিয়ে যাচ্ছে? বা ভুল করে ঢুকছে? |
| **NULL** | কোনো Column `NULL` হলে `=`, `NOT IN`, `COUNT(*)` কী করবে? |
| **সমান মান (টাই)** | সর্বোচ্চে দুজন সমান থাকলে দুজনই আসবে? (`LIMIT 1` না) |
| **সীমানা** | `>` নাকি `>=`? বছরের শেষ দিন আছে? |
| **ভুল জায়গার শর্ত** | Row-এর শর্ত `WHERE`-এ, দলের শর্ত `HAVING`-এ? |
| **অগ্রাধিকার** | `AND` আর `OR` একসাথে থাকলে বন্ধনী আছে? |
| **একাধিক উত্তরের Subquery** | `= (SELECT ...)` একাধিক Row দিলে? (`IN`) |

তারপর, সময় থাকলে, **দ্বিতীয় একটা উপায়ে** একই প্রশ্ন লেখো (যেমন `JOIN`-এর জায়গায় `EXISTS`)। দুটো আলাদা রাস্তা একই উত্তরে পৌঁছালে আত্মবিশ্বাস অনেক বাড়ে।

## টুকরোগুলোর নাম দাও: CTE

বড় প্রশ্নে ছোট প্রশ্নগুলো যখন অনেক হয়, Subquery-র ভেতরে Subquery পড়া কঠিন হয়ে যায়। তখন প্রতিটা ছোট প্রশ্নকে `WITH` দিয়ে **নাম** দিয়ে রাখো (লেভেল ৪.৩)। তোমার ভাঙার ধাপগুলোই তখন Query-র গঠন:

<Run db="q3-shop">
```sql
WITH
-- ছোট প্রশ্ন ১: ২০২৫-এর প্রতিটা অর্ডারের টাকা
orders_2025 AS (
  SELECT o.order_id, o.cust_id, p.price * o.quantity AS amount
  FROM orders o
  JOIN product p ON p.prod_id = o.prod_id
  WHERE o.order_date >= '2025-01-01' AND o.order_date < '2026-01-01'
),
-- ছোট প্রশ্ন ২: প্রতি ক্রেতার যোগফল
per_customer AS (
  SELECT cust_id, COUNT(*) AS orders_2025, SUM(amount) AS total
  FROM orders_2025
  GROUP BY cust_id
)
-- বড় প্রশ্ন: ঢাকার, ৪০,০০০-এর বেশি
SELECT c.cname, pc.orders_2025, pc.total
FROM per_customer pc
JOIN customer c ON c.cust_id = pc.cust_id
WHERE c.city = 'Dhaka' AND pc.total > 40000
ORDER BY pc.total DESC;
```
</Run>

একই উত্তর। প্রতিটা `WITH`-অংশ নিজেই একটা ছোট প্রশ্নের উত্তর, আর আলাদা করে পরীক্ষা করা যায়: শেষের `SELECT`-টা বদলে `SELECT * FROM per_customer;` লিখে চালাও (বদলে দেখো)। লক্ষ্য করো, `HAVING` এখানে `WHERE` হয়ে গেছে: যোগফলটা আগের ধাপেই একটা সাধারণ Column (`total`) হয়ে গেছে।

## আটকে গেলে

- **প্রশ্নটা ছোট করো।** "ঢাকার, ২০২৫-এর, ৪০,০০০-এর বেশি" না পারলে আগে শুধু "প্রতি ক্রেতার মোট খরচ" লেখো। তারপর একটা একটা শর্ত যোগ করো।
- **একজনের জন্য লেখো।** "প্রত্যেকের নিজের ব্রাঞ্চের গড়" কঠিন লাগলে আগে "ব্রাঞ্চ ১০৩-এর গড়" লেখো। তারপর `103`-এর জায়গায় বাইরের Row-এর Column বসাও। Correlated Subquery এভাবেই জন্মায়।
- **উল্টো করে বলো।** "সবগুলো নিয়েছে" = "এমন কোনোটা নেই যেটা নেয়নি"। "কখনো না" = "সবাই − যাঁদের আছে"।
- **Error-টা পড়ো।** `ambiguous` = alias দাও। `Invalid use of group function` = Aggregate `WHERE`-এ বসেছে। `Subquery returns more than 1 row` = `=` বদলে `IN`।
- **Row গোনো।** প্রতিটা JOIN-এর পর `SELECT COUNT(*)`। হঠাৎ বেড়ে যাওয়া বা কমে যাওয়া প্রায় সব ভুলের প্রথম চিহ্ন।

<Tip title="পরীক্ষার খাতায়">
প্রশ্ন অস্পষ্ট হলে (`>` নাকি `>=`? রিটেক গুনব কি না?) Query-র ওপরে **এক লাইনে নিজের ধরে নেওয়াটা লিখে দাও**। পরীক্ষক তোমার Query তোমার ধরে নেওয়া অনুযায়ী মিলিয়ে দেখবেন। ধাপ ২-এর টেবিলটাও খাতায় ছোট করে লিখলে আংশিক নম্বর পাওয়ার সম্ভাবনা বাড়ে, Query-তে ছোট ভুল থাকলেও।
</Tip>
