## প্রথম প্রশ্ন: বেশি Column, নাকি বেশি Row?

JOIN লেখার আগে একটা জিনিস পরিষ্কার করে নিই। SQL-এ দুটো টেবিলের তথ্য একসাথে করার **দুটো আলাদা** উপায় আছে:

- **JOIN** বিভিন্ন টেবিলের **Column** পাশাপাশি জোড়ে।
- **Set Operator** (`UNION`, `UNION ALL`) একটার নিচে আরেকটা বসিয়ে **Row** জোড়ে।

<ColsVsRows />

মনে রাখার সহজ উপায়: দুটো স্প্রেডশিট। **পাশাপাশি** রাখলে Column বাড়ে, সেটা JOIN। একটার **নিচে** আরেকটা রাখলে Row বাড়ে, সেটা Set Operator।

তাই Query লেখার আগে নিজেকে জিজ্ঞেস করো: **"আমার কি বেশি Column দরকার, নাকি বেশি Row?"** কাস্টমারের নামের পাশে তাঁর অর্ডারের তারিখ চাই? বেশি Column, মানে JOIN। কাস্টমার আর কর্মী, সবার নাম একটা লম্বা তালিকায় চাই? বেশি Row, মানে UNION:

<Run db="join-shop">
```sql
-- বেশি Row: দুই টেবিলের নাম একটা তালিকায় (UNION, পুরোটা লেভেল ১২-এ)
SELECT name, 'customer' AS type FROM customers
UNION ALL
SELECT name, 'employee' FROM employees
ORDER BY type, name;
```
</Run>

৯টা Row: ৫ জন কাস্টমার আর ৪ জন কর্মী, একটার নিচে আরেকটা। কোনো Column বাড়েনি। এই লেভেল আর পরেরটা পুরোটাই প্রথম ধরনের: **বেশি Column, মানে JOIN।**

## যখন JOIN লাগেই না

ধরো কেউ বলল: "সব কাস্টমার আর সব অর্ডার দেখাও।"

খেয়াল করো, এখানে দুটো টেবিলকে **সম্পর্কিত** করতে বলা হয়নি। শুধু দুটো তালিকা চাওয়া হয়েছে। তাহলে JOIN-এর দরকারই নেই: দুটো আলাদা Query, দুটো আলাদা ফলাফল।

<Run db="join-shop">
```sql
SELECT * FROM customers;
SELECT * FROM orders;
```
</Run>

দুটো ফলাফলের টেবিল এল, কারণ একসাথে করার কোনো প্রয়োজনই ছিল না। JOIN তখনই লাগে, যখন **সম্পর্কিত তথ্য একটাই ফলাফলে** দেখাতে হয়: "এই কাস্টমারের পাশে তাঁরই অর্ডার।"

## INNER JOIN: শুধু মিল থাকা ডেটা

ম্যানেজারের নতুন অনুরোধ: **"প্রতিটা কাস্টমার আর তাঁদের দেওয়া অর্ডারগুলো, এক রিপোর্টে।"**

এবার দুই টেবিলেরই তথ্য লাগবে। দুটো জুড়ে আছে একটা সাধারণ Column দিয়ে: `customer_id`। `customers`-এ এটা প্রত্যেকের পরিচয় (Primary Key), `orders`-এ এটা বলে অর্ডারটা কার (Foreign Key)। SQL এই মান মিলিয়ে বোঝে কোন অর্ডার কোন কাস্টমারের।

শেখার সময় সব Column দেখে নেওয়া ভালো, তাই প্রথমে `SELECT *`:

<Run db="join-shop">
```sql
SELECT *
FROM customers
INNER JOIN orders ON customers.customer_id = orders.customer_id
ORDER BY orders.order_id;
```
</Run>

পড়ার উপায়: "`customers` নাও; প্রতিটা কাস্টমারের পাশে `orders`-এর সেই Row-গুলো বসাও, যেখানে দুই পাশের `customer_id` সমান।"

- `ON` বলে দেয় **কোন Column দিয়ে মেলাবে**। সাধারণত একপাশে Primary Key, অন্যপাশে Foreign Key।
- শুধু `JOIN` লিখলেও সেটা `INNER JOIN`।

এবার গুনে দেখো: **৬টা Row।** কে কে নেই?

<JoinMatch mode="inner" />

- **Nabila আর Tanvir** নেই: তাঁদের কোনো অর্ডার নেই, `orders`-এ মেলার মতো কিছু পাওয়া যায়নি।
- **অর্ডার 106** নেই: তার `customer_id` ৯, আর `customers`-এ ৯ নেই।

এটাই `INNER JOIN`-এর স্বভাব: **শুধু সেই Row রাখে, যার দুই টেবিলেই মিল আছে।** একজন কাস্টমার অর্ডার দিয়ে থাকলে আসবেন; না দিয়ে থাকলে আসবেন না, কারণ `orders`-এ তাঁর জোড়া নেই। একইভাবে কোনো অর্ডারের কাস্টমার না মিললে সেটাও আসবে না।

<JoinVenn kind="inner" />

<Analogy>
বিয়ের অনুষ্ঠানে দুটো তালিকা: অতিথিদের নাম, আর আসনের তালিকা। `INNER JOIN` হলো এমন একজন স্বেচ্ছাসেবক, যে শুধু তাদের বসায় যাদের নাম **দুই তালিকাতেই** আছে। যার আসন নেই, বা যে আসনে কারো নাম নেই, তারা এই তালিকায় আসবে না। (তাদের খোঁজ পরের লেভেলে।)
</Analogy>

## দরকারি Column আর ছোট নাম (Alias)

`SELECT *` দিয়ে JOIN বোঝা সহজ, কিন্তু ফলাফলে `customer_id` দুবার, আর এমন অনেক Column যা রিপোর্টে কারো কাজে লাগে না। আসল প্রজেক্টে শুধু সেই Column নাও, যা রিপোর্টে দরকার: কাস্টমারের নাম, অর্ডার নম্বর, তারিখ, টাকা।

আর প্রতিবার `customers.` আর `orders.` লেখা ক্লান্তিকর। অভিজ্ঞ ডেভেলপাররা টেবিলকে ছোট নাম (**Alias**) দেন: `customers c`, `orders o`:

<Run db="join-shop">
```sql
SELECT c.name, o.order_id, o.order_date, o.amount
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
ORDER BY o.order_date;
```
</Run>

| name | order_id | order_date | amount |
| --- | --- | --- | --- |
| Rahim | 101 | 2026-01-05 | 900.00 |
| Rahim | 102 | 2026-01-12 | 1800.00 |
| Karim | 103 | 2026-02-03 | 1200.00 |
| Sumaiya | 104 | 2026-02-20 | 2500.00 |
| Sumaiya | 105 | 2026-03-08 | 1350.00 |
| Karim | 107 | 2026-04-01 | 1800.00 |

তিনটা লাভ: Query পড়া সহজ, কম ডেটা আনতে হয় বলে দ্রুত, আর রিপোর্ট পরিষ্কার।

- `FROM customers c` মানে এই Query-তে `customers`-কে ডাকব `c` নামে (`AS` লেখা ঐচ্ছিক)।
- Alias দেওয়ার পর পুরো Query-তে সেটাই লিখতে হবে; `customers.name` লিখলে তখন error।
- দুই টেবিলে একই নামের Column থাকলে (যেমন `customer_id`) সামনে টেবিল বা Alias দেওয়া **বাধ্যতামূলক**।

<Remember>
**শুধু দুই টেবিলেই আছে এমন রেকর্ড চাই? তাহলে `INNER JOIN`।** এটা SQL-এর সবচেয়ে বেশি ব্যবহৃত JOIN, আর বাকি সব JOIN বোঝার ভিত্তি।
</Remember>

## JOIN + WHERE + GROUP BY: আসল রিপোর্ট

JOIN করার পর ফলাফলটা একটা সাধারণ টেবিলের মতোই; আগের লেভেলের সব কিছু তার ওপর চলে। ঢাকার কাস্টমারদের অর্ডার, বড় অঙ্ক আগে:

<Run db="join-shop">
```sql
SELECT c.name, o.order_id, o.amount
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.city = 'Dhaka'
ORDER BY o.amount DESC;
```
</Run>

প্রতিটা কাস্টমার মোট কত টাকার কেনাকাটা করেছেন:

<Run db="join-shop">
```sql
SELECT c.customer_id, c.name, COUNT(*) AS orders, SUM(o.amount) AS total
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY total DESC;
```
</Run>

| customer_id | name | orders | total |
| --- | --- | --- | --- |
| 3 | Sumaiya | 2 | 3850.00 |
| 2 | Karim | 2 | 3000.00 |
| 1 | Rahim | 2 | 2700.00 |

`GROUP BY c.customer_id, c.name` কেন, শুধু `c.name` না? দুজন "Rahim" থাকলে নাম ধরে দল বানালে দুজনের টাকা মিশে যেত। আইডি ধরে দল বানানোই নিরাপদ।

আর লক্ষ্য করো: **Nabila আর Tanvir তালিকায় নেই।** মার্কেটিং টিম যদি বলে "সব কাস্টমার চাই, যাঁরা এখনো কিছু কেনেননি তাঁরাও, যাতে তাঁদের অফার পাঠানো যায়", তাহলে `INNER JOIN` চলবে না। সেটাই পরের লেভেলের প্রথম পাঠ।

## ON ভুলে গেলে কী হয়

`ON` বলে দেয় কোন Row কার পাশে বসবে। সেটা না দিলে (পুরোনো কমা-লেখায় `FROM customers, orders`) MySQL প্রতিটা কাস্টমারকে প্রতিটা অর্ডারের পাশে বসায়:

<Run db="join-shop">
```sql
SELECT COUNT(*) AS rows_without_on FROM customers, orders;
```
</Run>

৫ × ৭ = **৩৫টা** অর্থহীন Row: Rahim-এর পাশে Karim-এর অর্ডারও। একে বলে **Cartesian Product**। লাখো Row-এর টেবিলে এটা সার্ভার বসিয়ে দিতে পারে। তবে ইচ্ছা করে করলে এটা কাজেরও হয়: সেটার নাম `CROSS JOIN`, লেভেল ১১-এ।

<BugMonster title="JOIN-এর প্রথম ফাঁদগুলো">

**১. `ERROR 1052: Column 'customer_id' in field list is ambiguous`।** দুই টেবিলেই `customer_id`। কোনটা চাও বলে দাও: `c.customer_id`।

**২. ভুল Column দিয়ে মেলানো।** `ON o.product_id = c.customer_id` লিখলে MySQL কোনো error দেবে না, কারণ দুটোই সংখ্যা! কিন্তু কাস্টমার ১-এর পাশে বসবে পণ্য ১-এর অর্ডার। ফলাফল দেখতে "ঠিক" লাগে বলে এটা সবচেয়ে বিপজ্জনক বাগ। নিয়ম: **Foreign Key মেলে, যে টেবিলের দিকে সে তাকায়, তার Primary Key-র সাথে।** `o.customer_id` মিলবে `c.customer_id`-এর সাথে।

**৩. JOIN-এর পর সংখ্যা ফুলে যাওয়া।** কাস্টমার আর অর্ডার জোড়ার পর `COUNT(*)` দিয়ে কাস্টমার গুনলে ৬ আসবে, ৩ না, কারণ প্রত্যেকে দুবার এসেছেন। কাস্টমার গুনতে `COUNT(DISTINCT c.customer_id)`।

**৪. Alias দেওয়ার পর আসল নাম।** `FROM customers c` লিখলে বাকি Query-তে `customers.name` error দেবে; `c.name` লেখো।

</BugMonster>

<Quest id="1" title="বড় অর্ডারের কাস্টমার">

<Solution>

<Quest id="2" title="শহরভিত্তিক বিক্রি">

<Solution title="ইঙ্গিত">

<Run db="join-shop">
```sql
SELECT c.name,

       SUM(o.amount)     AS total,

FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
HAVING SUM(o.amount) > 2800
ORDER BY total DESC;
```
</Run>
